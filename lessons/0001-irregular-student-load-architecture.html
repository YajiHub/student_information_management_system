Modeling Irregular Student Unit Loads

Tied to: Enterprise RESTful API Development for SIMS

The Core Problem

In standard academic systems, regular students follow fixed cohort blocks (e.g., Block 4A takes exactly 21 prescribed units in Semester 1). However, real-world institutions have irregular students who:

  • Carry failed prerequisites requiring off-sequence retakes.
  • Face academic probation with reduced credit unit caps (e.g., 12 or 15 units instead of 24).
  • Mix courses across multiple year levels and section schedules.
Key Insight: Never assume a uniform semester load. Unit limits must be an explicit, student-level attribute, validated transactionally on every enrollment request.

Relational Schema Design

In PostgreSQL and Prisma, we represent irregular status with an enum and an explicit credit ceiling on the Student model:

enum StudentType {
  REGULAR
  IRREGULAR
}

model Student {
  id                Int         @id @default(autoincrement())
  student_number    String      @unique
  student_type      StudentType @default(REGULAR)
  max_allowed_units Int         @default(24)
  // ... other attributes
}

The Enrollment Validation Pipeline

When an admin or advisor attempts POST /api/v1/enrollments with { student_id, course_offering_id }, the backend executes three sequential checks:

  1. Section Capacity Check: Verify active enrollments in target offering do not exceed offering.capacity.
  2. Duplicate Check: Verify student is not already enrolled in this offering (enforced by @@unique([student_id, course_offering_id])).
  3. Term Load Summation: 
    // 1. Fetch current enrolled units in the offering's term
